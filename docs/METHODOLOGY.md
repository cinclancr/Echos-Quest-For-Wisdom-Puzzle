# Methodology

## Principles

1. **Byte-exact sources.** The story is verified by SHA-256 before any
   analysis; two tokenisation conventions are maintained simultaneously
   (dCode-style and apostrophe-preserving) and every hypothesis states which
   one it depends on.
2. **Pinned wordlist.** The BIP39 English wordlist is pinned by hash and
   anchor indices (`armed=94`, `strong=1721`, ...) are asserted at load.
3. **Read-only.** Derivation is address-computation only: hash160 of
   derived public keys compared against the target. No signing, no
   transaction, no network.
4. **Coverage honesty.** Every negative result states exactly what was and
   was not derived. Checksum *counting* is never conflated with address
   *testing*.
5. **Independent implementations.** The Python toolkit and the C scanner
   implement the same pipeline twice; the C selftest cross-checks each
   layer against official vectors and against OpenSSL.
6. **No result fabrication.** A checksum-valid arrangement is not treated
   as a solution; only an address match is, and it must reproduce under
   the second implementation before any claim is made.

## The no-checksum turn

The maintainer's observation that the mnemonic may be checksum-invalid
changed the search space by 16x. Three response layers:

* **Validators** derive any 12-word candidate regardless of checksum,
  reporting checksum status as information.
* **Natural-order battery** covers story-grounded orders under both KDFs,
  many paths/passphrases/encodings.
* **C scanner** enumerates ALL 11! arrangements of a word set (exactly
  itertools order), checkpointed, in two modes: `full` (BIP39 KDF,
  primary path, both encodings) and `electrum1` (Electrum version-tag
  filter + Electrum KDF at m/0/0).

## Validation matrix (what proves the tools correct)

| Layer | Reference | Check |
|---|---|---|
| PBKDF2-HMAC-SHA512 | Trezor vectors.json[0] (mnemonic + TREZOR passphrase) | exact 64-byte seed |
| BIP32 master + CKD | BIP-0032 spec vector 1 | xprv strings |
| BIP44 chain + P2PKH | golden h160s generated by the validated Python stack | 16/16 goldens |
| secp256k1 (fast C) | OpenSSL EC on 1000+ scalars | compressed + uncompressed bytes |
| base58check | target address decode/roundtrip | version byte + hash160 |
| checksum counter | prior Python enumeration total (2,492,947 for the midpoint set) | exact equality |

## Statistical discipline

Multiple-testing is the main trap in this puzzle: dozens of window sizes,
filters and orderings guarantee occasional "interesting" outputs by chance.
The repository therefore: (a) registers extraction rules before evaluating
them (results/extractions.csv), (b) quantifies the 1/16 checksum-valid
coincidence rate, (c) reports coverage rather than p-values, and (d) marks
any finding that requires post-hoc parameter fitting as INCOMPLETE.
